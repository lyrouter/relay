## 1. 防的是什么

RLS 把跨租户**读**堵死了 —— 这一点 §4.2 做得很彻底，负测也覆盖了裸 SQL。
**但 PostgreSQL 做外键检查时绕过 policy。**

所以在单列外键下：

- 租户 A 能插一行引用租户 B 的用户（例如把 B 的用户加进 A 的空间）；
- **读上不漏** —— join 什么也查不到，因为父行对 A 始终不可见。这正是危险的地方：
  一套只做读负测的检查会认为这是干净的；
- 但 **B 删那个用户时，cascade 会打进 A 的数据**。

这是一次跨租户**写**，由一个从来没有权限、而且事后看不出发生过什么的租户执行。
MT 存在的意义就是关这类门。

实测确认过（`tests/test_cross_tenant.py::test_cannot_reference_another_tenants_row`
在改之前是失败的）。

## 2. 为什么现在批而不是以后再说

和 §8.4 那三个字段（`rev` / `actor_type` / `ticket_external_ref`）完全同构，
是你们已经接受过的同一条逻辑：

> **建表时加最便宜，事后补最贵。**

现在近乎免费。事后要迁 **32 个外键**。

## 3. 批了等于接受三件事

| 代价 | 说明 |
|---|---|
| **28 个额外唯一索引** `(id, tenant_id)` | 不是冗余设计，是 PG 硬性要求：外键指向的列必须有唯一约束。内部工具这个量级可以忽略 |
| **PostgreSQL 15+ 底线** | 有 11 个外键用了 `ON DELETE SET NULL (column)` 这个列表形式（PG 15 才有）。不用它的话，普通 `SET NULL` 会连 `tenant_id` 一起置空，而它是 NOT NULL —— **删除会在运行时炸，不是在评审时**。目前文档里没写最低版本 |
| **建模写法变了** | 所有跨表引用写 `tenant_fk(...)` 而不是 `ForeignKey(...)`，有结构性测试兜底（`test_every_cross_table_reference_is_tenant_scoped`） |

## 4. 考虑过但否掉的替代方案

**把主键本身做成复合 `(tenant_id, id)`** —— 那 28 个索引就省了，外键直接指主键。

否掉的理由：每次 `session.get()` 都要传元组，每个路由和序列化器都要带两个值。
为省 28 个索引不值。

## 5. 不批也站得住

如果你认为 MT 的职责边界就是**读**隔离，那就回退成单列外键，跨租户引用改到服务层校验。

**我不推荐** —— §4.2 明确说过不要把架构安全押在应用层纪律上，而这正好是同一件事：

> 任何 ORM 都留了裸 SQL 出口，把架构安全押在 ORM 能力上是最该避开的选择。

服务层的租户匹配校验，和 ORM 层的租户过滤，是同一类会被忘记调用的东西。

## 6. 批了会改三处

1. **§4.2** 加一段：外键为什么必须复合，附「RLS 不覆盖引用完整性」这个前提；
2. **§12.1** 加一条 **S-18**（S-15 / S-17 已退役重编为 F / R，不复用编号）；
3. **§2.4 / D-0** 补上 PostgreSQL **最低 15**，理由挂在 `ON DELETE SET NULL (column)` 上。
