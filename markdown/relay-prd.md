## 0. 产品定位与关键判断

### 0.1 产品定位

**定位**：**面向 AI Native 团队的协作平台**——服务所有在生产环境运行 AI 系统的团队，AI Gateway 团队是其中的首个部署实例与参考实现。

**一句话**：
> 把告警、对话、工单、代码、遥测数据收敛到同一条上下文链上，让人和 Agent 都能推理"到底发生了什么"。

**为什么面向"AI 团队"这个范围成立（而非稀释）**

`trace_id`、`provider`、`model`、`error_code`、`blast_radius` 本来就是 **AI 运维的通用字段**，而非 Gateway 专属——跑 RAG 应用、Agent 产品、模型服务的团队同样需要。真正 Gateway 专属的只有 `gateway_version` 与路由策略相关字段。因此正确做法是**把 schema 做成可配置**，而不是删掉领域细节。

**为什么 AI 团队的痛感结构性更强**（这是定位的立论基础，非营销话术）：

| 差异 | 说明 |
|---|---|
| **故障无法从堆栈还原** | 传统服务确定性失败，给你行号；AI 系统概率性失败。还原一次故障需要 trace + 模型版本 + prompt 修订 + 检索上下文 + 供应商当时状态，分散在五个系统里，缺一项调查即停滞 |
| **"昨天还好好的"是真实故障模式** | 供应商静默更新模型、prompt 漂移、检索语料过期。代码没变而行为变了，**变更归因必须能伸到自己 commit 之外** |
| **关键路径不由自己控制** | 供应商故障、限流、模型下线是只能吸收不能修复的事件，这让故障史价值倍增——上季度的处置往往就是这季度的答案 |
| **成本是运维信号而非财务报表** | Token 消耗随流量、路由、模型选择每日波动，应与延迟曲线并列，而非躺在月度报表里 |
| **知识以周为单位衰减** | 模型能力、API 面、最佳实践的更替速度，快到静态 wiki 在无人察觉时就已过期 |

### 0.2 适用边界（必须明确写出）

> **Relay 假设你在生产环境运行 AI 系统，且有值得关联的遥测数据。这个假设就是边界。**

- ✅ 适用：跑 AI Gateway、RAG 应用、Agent 产品、模型服务、或产品中含 AI 功能的团队
- ❌ 不适用：没有 trace、eval、供应商依赖可供推理的团队——对他们而言 Relay 只是个更差的 Linear

**泛化到"AI 团队"≠ 泛化到"所有团队"。** 不做通用文档协作，不对标 Notion。这条边界一旦模糊，产品会迅速退化为"又一个 Jira + Confluence"，丧失全部差异化。

### 0.3 ⚠️ 仍需确认的判断

**判断一：周期 12 周，但 MVP 的硬性验收边界定在第 6 周的里程碑 A。**
把三项高风险/高成本工作划入 Phase 2 后，MVP 净工作量约 13.5 人·周。**周期没有跟着压缩，这是刻意的**——余下的约 7 人·周不用来提前交付，而是用来给 Phase 2 三项争取充足的实施与灰度时间：GitHub 同步在第 7–12 周以 Phase 2 身份开工，可拿到约 6 周灰度期。
换来的确定性是：**第 6 周有一个不含任何高风险项的、必然可交付的 MVP**——「MVP 是否成立」与「GitHub 同步是否做扎实」互不牵连。§4.10 给出工作量拆解与里程碑划分。

**判断二：群内建单只做 `@Relay` 触发，不做全群消息自动监听。**
"识别群内的问题并提 Issue"若理解为被动监听全部消息并自动判断，MVP 阶段误报代价过高（打扰 + 隐私顾虑 + 成本），且团队会很快把机器人静音。§4.8 给出了折中方案：高置信度时**私聊提醒发言人**，不打扰全群。

**判断三：取消 SSO 后，身份绑定成为机器人可用性的前置条件。**
没有通讯录同步，平台不知道群里说话的人是谁。§4.5 设计了三元身份绑定（平台账号 ↔ 企微 userid ↔ GitHub handle），**未绑定用户无法使用机器人建单**。这是取消 SSO 的直接代价，需在推广时提前告知团队。

> 正因如此，三元身份绑定**留在 MVP 内**。GitHub 同步排在 Phase 2，因此绑定项中的 **GitHub handle 在 MVP 内价值有限**（其用途——@提及翻译、PR 关联、责任人映射——全部服务于同步），但**企微 userid 绑定是机器人的硬前置**，砍掉则机器人整体不可用。
> 连带影响：**身份绑定率是机器人可用性的天花板**，也就成了 MVP 验收指标（§4.11 要求 >90%）。建议里程碑 A 期间就做一次全员绑定推动，而非等机器人上线才推。

**判断四：两个架构性前置项不可推后，尽管它们在 MVP 内没有直接消费方。**
多租户数据模型（1.5 人·周）与遥测适配器抽象（1 人·周）都是**不做就要返工**的架构性工作。
**必须诚实指出一点**：遥测适配器的四个消费方（告警建单、变更归因、ChatOps 只读、环境快照）全在 Phase 2+，而 RAG 与自有网关同样在 Phase 2，因此 MVP 内**唯一还用到它的只有 §4.3 的 AI 上下文字段填充，且该字段在 MVP 阶段基本为空**。也就是说这 1 人·周在 MVP 里**看不到任何可演示的产出**。
结论仍是**做**——理由不变（Phase 2 有四处返工，返工成本远高于 1 人·周），但需向团队讲清这是**技术债预付**而非功能交付，否则第 2 周的评审上它很容易被当成"没做出东西"而被挤掉。

**判断五：MVP 的「AI 价值」只由一项承载，这是范围划分的主要代价，且未被消除。**
§4.0 论证过 MVP 必须同时承载**替代价值**与**AI 价值**，缺一不可——若首次体验只是"换了个 Jira"，后续再好的 AI 功能也很难挽回热情。RAG 问答排在 Phase 2 后，MVP 的 AI 触点只剩**机器人 AI 生成工单草稿**（§4.8③ 第 ③ 步）。
这条风险没有技术解，只有两个现实选项：
1. **接受它**，并把「AI 生成草稿」的体验做到足以让人记住——草稿质量（确认率 >60%，见 §4.11）因此从"体验指标"升级为**MVP 唯一的 AI 价值证明点**，不可打折；
2. 若团队反馈第 6 周的双轨试用"感觉就是个 Jira"，则应把 RAG 的优先级从第 7–12 周的第二位**提到第一位**（即先 RAG 后 GitHub 同步），而不是等 Phase 2 排完底座。
**这是需要在里程碑 A 复盘时带着真实反馈判断的事项，现在不预设结论。**

## 2. 能力规格

### 2.1 告警语义收敛与 AI 分析简报 【M3】

**问题**：一次供应商故障会同时触发 5xx 率、P99 延迟、重试激增、熔断开启、配额异常等十余条告警。仅靠"聚合窗口 + 免打扰"只是**消息层降噪**，值班人依然要自己拼图。

**收敛维度**（逐级判定，命中即归并）：

| 维度 | 规则 |
|---|---|
| 同实体 | 相同 provider / model / tenant / instance |
| 时间窗 | 5 分钟滑动窗口内 |
| 拓扑因果 | 上游 provider 5xx → 重试激增 → 延迟上升 → 熔断，识别为一条因果链 |
| 指纹相似 | 告警规则 + 标签集合的相似度 > 0.8 |
| 已知抑制 | 在维护窗口内 / 已存在活跃 Incident → 挂载而非新建 |

**输出**：一个 `Incident` 聚合体，包含 N 条原始告警、因果链视图、首发告警标记。

**告警风暴保护**：单位时间告警数超阈值时自动进入强聚合模式，只推送聚合体，原始告警仅在详情页可查。

**AI 分析简报（SLA：告警后 60 秒内）**

固定六段式，因为值班时人只想看这六件事：

```
【发生了什么】provider=azure-openai 的 5xx 率从 0.3% 升至 7.2%，
              持续 4 分钟，首发告警 14:21:03
【影响面】   3 个租户（tenant-a 占 68%）｜ gpt-4o、gpt-4o-mini
              ｜ 影响 QPS 占比 12% ｜ 失败请求 1,284 次
【近期变更】 ⚠️ 14:18 完成灰度批次 2 推进（PR #892，@李工）
              ⚠️ 供应商侧状态页 14:15 报告 degraded
【相似历史】 #217（2026-05）症状一致，根因为供应商区域故障，
              处置：切流至备用区域，耗时 8 分钟
【建议动作】 1. 切流至 azure-eastus2（历史有效）
              2. 若无效，回滚灰度批次 2
【置信度】   中 —— 供应商状态页与灰度推进时间接近，无法直接排除后者
```

> **必须标注置信度并保留多个假设**，不能把 AI 推测写成结论。值班人在压力下容易照单全收，简报的措辞责任很重。

### 2.2 ChatOps 自然语言运维 【M3】

#### Tier 1 · 只读（Phase 2，无审批阻塞）

| 命令示例 | 工具 |
|---|---|
| "azure 现在延迟多少" | `query_latency(provider, model, tenant, window)` → P50/P95/P99 |
| "tenant-a 最近一小时错误率" | `query_error_rate(dimensions, window)` |
| "tenant-b 配额用了多少" | `query_quota(tenant)` |
| "抓 5 条最近的 429 样本" | `sample_requests(filter, n)` → **默认脱敏，不含 payload** |
| "现在路由策略是什么" | `get_routing_config()` |
| "各供应商健康状态" | `get_provider_health()` |
| "最近 2 小时有什么部署" | `list_recent_changes(window)` |
| "限流模块有哪些 open issue" | `search_tickets(filter)` |

输出统一为**卡片 + 小图**，而非纯文本数字，值班场景下可读性优先。

#### Tier 2 · 可写（Phase 4，**已决策采纳**）

##### ① 核心设计原则：ChatOps 写操作是「止血」，不是「变更」

这条原则统领本节全部设计：

> **ChatOps 的每一次写操作，默认都是临时的、带 TTL 的、会自动回滚的。**

需要永久生效的配置调整，一律走 M0 变更管理的正规流程。这条区分把 ChatOps 的风险面从"生产配置管理"压缩到"临时应急干预"，是整个安全模型成立的前提。

##### ② 动作白名单（可配置，Gateway 场景为参考实现）

> **为什么白名单必须可配置**：不同团队的可逆运维动作不同——Gateway 团队关心切流与提额，RAG 产品团队可能关心重建索引与切换检索策略。因此白名单为**部署时配置**，但配置**必须满足四条硬约束**：动作可逆或影响可控、有明确 TTL、有影响面预估接口、有回滚实现。不满足者不得入白名单。
>
> 以下 5 项是 Gateway 场景的参考实现，也是配置合法性的判断样例。

| 动作 | 参数 | 默认 TTL | 影响面计算 | 回滚方式 |
|---|---|---|---|---|
| `切流/摘除供应商` | provider、目标供应商、scope（tenant/global） | 30 min | 受影响租户数、QPS 占比、目标供应商余量 | 恢复原权重 |
| `清缓存` | scope（tenant/model/global） | — | 缓存命中率、**预估回源 QPS 涨幅** | 不可回滚，但影响可控 |
| `临时提额` | tenant、新配额、时长 | 60 min | 该租户当前用量、集群总容量余量 | 恢复原配额 |
| `暂停灰度` | batch_id | 无（需显式恢复） | 已推进批次、受影响租户 | `恢复灰度` |
| `恢复灰度` | batch_id | — | 待推进租户数 | `暂停灰度` |

**TTL 到期自动回滚**，到期前 5 分钟在原群提醒："切流将于 5 分钟后自动恢复，需要延长吗？"延长同样需要双人确认。

> ⚠️ `清缓存` 是 5 项中唯一不可回滚的，且有**缓存雪崩**风险（全局清空 → 回源 QPS 瞬时暴涨）。dry-run 必须显式给出预估回源涨幅；`scope=global` 建议默认禁用，仅允许 tenant/model 级。

##### ③ 执行流程

```
自然语言输入
  ↓
① LLM 解析为结构化命令 —— 解析失败或存在歧义则拒绝，绝不猜测
  ↓
② 回显结构化命令 —— 卡片展示 action/参数/scope/TTL
     后续确认与执行均针对【结构化命令】，原始自然语言不再参与
  ↓
③ 权限校验 —— 继承发起人在 Gateway 的 RBAC，绝不放大
  ↓
④ 真实 dry-run —— 查询线上当前状态计算影响面，非模拟
  ↓
⑤ 双人确认 —— 卡片等待第二人点击，5 分钟未确认自动失效
  ↓
⑥ 执行 —— 幂等；卡片原地更新执行状态
  ↓
⑦ 自动生成变更单 + 全量审计 + TTL 计时开始
```

**第 ② 步是安全设计的关键**：自然语言只用于"生成候选命令"，一旦转为结构化命令，后续所有环节都与原始文本脱钩。这样即使输入包含提示注入，也无法越过白名单——因为能被执行的只有 5 个结构化动作。

##### ④ 双人确认机制

- **第二人资格**：具备该动作的 Gateway RBAC 权限，且**不能是发起人**
- **有效期**：卡片 5 分钟内未获确认自动失效，防止陈旧命令被误点
- **确认者留痕**：两人身份均写入变更单，共同担责

**凌晨单人值班的现实问题（必须设计逃生舱）**

双人确认在凌晨 3 点可能找不到第二个清醒的人。如果机制此时硬阻塞，工程师会直接绕过——登跳板机手工操作，**结果是更差的：没有审计、没有 TTL、没有变更单**。

因此设计**紧急单人执行**通道：

| 条件 | 要求 |
|---|---|
| 触发前提 | 存在活跃 P0/P1 Incident，且已呼叫第二人超时 3 分钟无响应 |
| 代价 | TTL 缩短至 10 分钟；需填写一句话理由 |
| 通知 | 立即通知全体 on-call + 上级 + 值班群，**不可静默** |
| 事后 | 强制 24h 内补充复盘说明，未补则锁定该用户 ChatOps 写权限 |
| 监控 | 紧急单人执行占比 **> 15% 视为机制设计失败**，需重新评估排班或降低确认门槛 |

> 设计取向：**不追求零绕过，而是让绕过路径本身是被观测、被约束、有代价的**。

##### ⑤ 安全信封（其余机制）

| 机制 | 说明 |
|---|---|
| 白名单 | 仅上述 5 项，硬编码，不可通过自然语言绕过 |
| 渠道限制 | **外部客户群、外部渠道零写权限**，硬性，无例外 |
| 变更冻结 | 冻结期内写操作需更高级别审批 |
| 熔断 | 单位时间写操作超 N 次自动锁定，需人工解锁；防止 Agent 异常循环 |
| 幂等 | 重复确认不产生二次执行 |
| 部分失败 | 执行失败时明确回显失败环节与当前状态，**绝不留下"状态未知"** |
| 全量审计 | 原始自然语言 + 结构化命令 + dry-run 结果 + 双方确认 + 执行结果 + TTL 回滚记录 |
| 卡片即凭证 | 确认卡片永久留在群内并原地更新状态，本身就是可追溯的操作凭证 |

##### ⑥ 明确不做（硬性边界）

版本回滚、实例重启、封禁 Key、删除配置、修改计费。这些不可逆或影响面过大，必须走正规变更流程。

##### ⑦ 上线前置条件

Tier 2 上线必须同时满足：
1. M0 变更管理已上线（写操作需生成变更单）
2. M0 On-call 排班已上线（双人确认需知道谁在值班）
3. Tier 1 只读已稳定运行 ≥ 1 个月，自然语言解析准确率 > 95%
4. 完成一次红队演练：验证提示注入无法越过白名单

### 2.3 客户情绪感知与升级链路 【M4】

**为什么重要**：只判断"答案对不对"是不够的——**情绪信号比置信度更早预示客户流失风险**。答案正确但客户已经第三次追问，机器人继续答就是在加速关系恶化。

**信号采集**（多信号加权，非单一情绪词判断）：

| 类别 | 信号 |
|---|---|
| 语言 | 负面情绪词、反问、感叹号密度、全大写 |
| **重复度** | "又"/"还是"/"第几次了"/"上次也说" —— **权重最高** |
| 节奏 | 追问间隔缩短、短时间连发多条 |
| 社交 | @ 多人、@ 对方高层、拉入新成员 |
| 商务 | 提及合同、续约、SLA、赔偿、投诉、竞品 |
| 历史 | 该客户未闭环工单数、近 30 天故障影响次数、历史情绪均值 |

**输出**：`sentiment_score`（当前情绪）+ `escalation_risk`（升级风险，含历史因素）

**动作矩阵**：

| 风险 | 机器人 | 工单 | 通知 |
|---|---|---|---|
| 低 | 正常回答 | — | — |
| 中 | 语气调整、优先给可执行动作、主动提供转人工 | 提升优先级 | 提示值班 |
| 高 | **立即静默**（哪怕答案正确） | 升级 P1、绑定客户档案 | @值班 + @客户经理 + 拉内部作战群 |
| 极高（商务信号） | 静默 | 升级 P0 | 通知客户成功负责人 + 管理层 |

**三条禁忌**：
1. **绝不向客户暴露情绪判断**——不说"我感觉到您有些着急"，这会激化对立
2. **不因情绪改变事实**——不能为安抚而给出不实承诺或过度乐观的时间预估
3. **情绪数据仅内部使用**，进入客户档案需符合合规要求，不外传

**客户健康度档案**：情绪趋势曲线 + 未闭环工单 + 故障影响次数 + 响应达标率 → 流失预警，每周推送给客户成功团队。

### 2.4 Git 变更自动归因与环境快照 【M2】

**归因逻辑**：Gateway 大部分故障源于变更，这是投入产出比最高的排查加速手段。

```
输入：告警时间 T、受影响模块/供应商/租户
  ↓
召回 [T-2h, T] 内的所有变更：
   部署记录、合并 PR、配置变更、灰度批次推进、
   路由策略调整、供应商侧状态变化
  ↓
排序打分：
   时间接近度 × 变更文件与故障模块的相关度
   × 该文件历史故障率 × 灰度批次与受影响租户的匹配度
  ↓
输出：嫌疑变更 Top 3 + 变更内容摘要 + 责任人 + 一键回滚入口
```

**环境快照**：字段不等于快照。需捕获**故障时刻的完整配置切片**——路由策略、限流规则、供应商权重与健康状态、灰度批次与租户映射、模型映射表、超时/重试配置。

真正的价值在 **diff**：自动对比故障时刻与上一稳定态的配置差异，很多时候差异本身就是答案。快照自动附在工单中，永久保存。

### 2.5 GitHub Docs 协同同步 【M5】

**为什么必须做**：工程师的大量知识本来就在仓库里，且**随代码版本演进，时效性天然可靠**——比人工维护的文档更不容易过期。

| 来源 | 处理 |
|---|---|
| `docs/**`、`README` | 解析为知识单元，`applies_to` 从 branch/tag 自动推断 |
| `CHANGELOG` | 版本变更知识，回答"X 版本改了什么" |
| `openapi.yaml` / spec | **结构化入库**，接口、参数、错误码可精确问答（非切片检索） |
| 错误码表 | 高权威知识，直出 |

**机制**：
- PR 合并触发同步，**PR 合并即知识生效**，与"写文档即训 Bot"是同一条链路
- 仓库文档默认 `authority: official`，高于平台内草稿；冲突时以仓库为准
- **反向能力**：平台内沉淀的知识可一键提 PR 回仓库，避免知识分叉
- Public Repo 的文档默认 `scope: public`，Private Repo 默认 `internal`

### 2.6 三项细化规格

**AI-DLP 双向脱敏**
- **出站**：外链分享、同步至 GitHub（Public Repo 规则更严）、对外群消息、机器人回答
- **入站**：内容进入向量库前脱敏——API Key、Token、客户名称、内网 IP、手机号、trace payload。**不脱敏就入库，等于把泄露风险永久固化进检索层**
- **检测**：正则 + 熵值检测（识别高熵字符串即密钥）+ 命名实体 + 自定义词典（客户名单）
- **动作**：阻断 / 掩码 / 告警 / 需审批；误报可白名单，放行须记录

**Trace 下钻**
- 卡片层：时间、租户、模型、供应商、路由决策路径、各阶段耗时、token、错误码、重试链
- 下钻层：完整 span 展开、查看同类请求、跳转 Gateway 控制台
- **payload 默认不可见**，查看需权限 + 审批 + 留痕
- Trace 卡片可嵌入日志、工单、IM 卡片，保持上下文一致

**FAQ 萃取（事件触发 + 批量）**
- 定时扫描已关闭工单与人工问答记录 → 语义聚类 → 生成 FAQ 草稿 → 按模块派给 owner 审核
- 与实时萃取互补：实时抓增量，批量补存量。冷启动阶段批量萃取尤其重要

## 3. 底座能力

### 3.1 变更管理闭环 【M0】
变更单（类型/影响面/回滚方案/审批人）→ 灰度批次定义 → 观察窗与自动回滚触发条件（错误率/延迟阈值）→ 变更冻结期。
**这是 §2.4 归因的前提**——没有结构化的变更单，就没有可归因的对象。

### 3.2 On-call 排班与升级 【M0】
排班表与轮转、代班与假期、L1→L2→主管的升级链路、响应超时自动升级、通知渠道递进（站内 → 应用消息 → 电话）。
告警与工单都默认了"通知到人"，这一节定义"人是谁"。

### 3.3 SLA 时钟 【M0】
按优先级 × 客户等级定义响应/解决时限；**等待客户回复时自动暂停计时**；工作日历；80% 时预警。有外部客户就绕不开。

### 3.4 AI 质量评测体系 【M6】

对 AI Native 产品，这是**基础设施而非可选项**。

| 维度 | 设计 |
|---|---|
| 数据集 | 影子模式标注数据 + 历史真实问答 + 人工构造边界 case（含越权诱导、注入攻击） |
| 触发时机 | 模型变更、Prompt 变更、知识变更、**Gateway 路由策略调整** |
| 指标 | 准确率、拒答准确率、引用有效率、延迟、成本、**跨租户泄露（必须为 0）** |
| 发布门禁 | 不达基线不允许发布，无例外 |
| 线上监控 | 采样人工复核 + 指标劣化自动降级（自动模式 → 副驾驶模式） |

> **网关路由策略调整也要触发评测**——这是"跑在自有网关上"的必然结果：网关换了模型，平台的 AI 质量就会变。这条链路如果不建，质量退化会完全无感知。
>
> 对 AI 团队而言这条尤其关键：**你的依赖会在你不知情时改变行为**（供应商静默更新模型）。定期基线回归是唯一的发现手段。建议除变更触发外，再加一条**每周定时全量评测**。

## 4. MVP 详细规格（Phase 1）

### 4.0 MVP 目标与边界

**一句话目标**：让团队停用 Jira，并在企微群里第一次感受到"平台知道我们在做什么"。
——注意后半句**只由「机器人 AI 生成工单草稿」一项承载**，RAG 问答在 Phase 2。

MVP 承载两个独立价值，缺一不可：

| 价值 | 承载功能 | 若缺失的后果 |
|---|---|---|
| **替代价值** | 日志 + 工单 + 看板 + 企微通知 | 没有替代品，团队不会迁移 |
| **AI 价值** | 企微机器人**群内建单 + AI 生成草稿** | 变成"又一个工单系统"，感受不到 AI Native |

> **AI 价值必须在 MVP 内出现，不能等 Phase 2。内部工具的采纳窗口只有第一周**，如果首次体验只是"换了个 Jira"，后续再好的 AI 功能也很难挽回热情。代价是周期拉长，见 §4.10。
>
> ⚠️ **必须正视的张力**：RAG 问答排在 Phase 2 后，MVP 的 AI 价值只剩建单草稿——这条风险是被**接受**的，不是被消除的。两条直接后果：
> ① 「AI 生成草稿」的确认率（>60%）从体验指标升级为 **MVP 唯一的 AI 价值证明点**，不可打折；
> ② 第 6 周双轨试用的团队反馈是**真实的检验**——若反馈确为"感觉就是个 Jira"，应把 RAG 提到第 7–12 周的第一优先，而非 GitHub 同步。见 §0.3 判断五。

**MVP 明确不做**：
- **⏸ 排在 Phase 2（规格保留，不打折）**：GitHub 双向同步 v1（§4.7）、RAG 问答引擎与知识种子（§4.9）、跑在自有 AI 网关上、日志「加入知识库」的向量化与索引（§4.6）、机器人的 RAG 问答与 👎 纠错（§4.8②）
- **Phase 2–4**：告警接入与 Auto-Ticket、ChatOps（Tier 1/2 全部）、外部客户群、情绪感知、变更归因与环境快照、SLA 时钟、On-call 排班、变更管理闭环、AI-DLP、复杂 RBAC、L4 外链分享、多人实时协同编辑、Trace 下钻、完整状态机、AI Copilot 撰写、MCP Server
- **多租户产品功能**：独立计费、租户自助管理、跨租户共享策略——⚠️ 注意**数据模型层多租户是 MVP 必做项**，见 §4.1

> ⚠️ **最后一条最容易被读反**：不做的只有多租户的**产品功能**，**数据模型必做**（§4.1）。误读的代价是数周量级的重构。

---

### 4.1 多租户数据模型（架构性前置项）

> **这是不可推迟、不可简化的一项。** 后期补做是数周量级的重构，现在做是 1–1.5 人·周。

**MVP 做什么（数据模型层多租户）**

| 项 | 要求 |
|---|---|
| `tenant_id` 贯穿 | 全部业务实体（用户、空间、日志、工单、知识单元、评论、附件、审计）均带 `tenant_id`，无例外 |
| 查询层强制过滤 | 在 ORM / Repository 层统一注入租户过滤，**不依赖业务代码自觉**，也不依赖提示词 |
| 索引设计 | 复合索引以 `tenant_id` 为前缀 |
| 向量库隔离 | 检索时租户过滤在**向量库查询条件中**执行，而非取回后再筛 |
| 越权测试 | 单元测试覆盖"跨租户读写必失败"，作为 CI 门禁 |

**MVP 明确不做（多租户产品功能）**
独立计费、租户自助管理后台、跨租户数据共享策略、租户级配置隔离、按租户的模型路由。这些是产品功能，可在有真实需求时再做。

**为什么这个区分重要**：很多团队把"多租户"理解为一整套产品功能而选择推迟，结果推迟的是**数据模型**——而数据模型是唯一无法低成本补做的部分。**先把 `tenant_id` 种进去，功能可以慢慢长。**

---

### 4.2 遥测适配器接口（架构性前置项）

**MVP 做什么**：定义适配器接口 + 实现 1 个适配器（自家 Gateway）。约 1 人·周。

```
interface TelemetryAdapter {
  queryMetrics(dimensions, timeWindow)      // 延迟、错误率、吞吐
  getTrace(traceId)                          // 单次请求链路
  sampleRequests(filter, n)                  // 请求样本（脱敏）
  listRecentChanges(timeWindow)              // 部署 / 配置 / 供应商变更
  getProviderHealth()                        // 依赖健康状态
  getCostBreakdown(dimensions, timeWindow)   // token 成本
}
```

**Phase 2+ 扩展目标**：LiteLLM、Portkey、OpenTelemetry、Langfuse、云厂商网关。

**为什么现在就要抽象**：告警建单、变更归因、ChatOps 只读、环境快照四个功能全部依赖这一层。若 MVP 直接硬编码调用自家 Gateway API，这四处都要在 Phase 2 返工——**返工成本远高于现在定义接口的 1 人·周**。

> ⚠️ **诚实提示**：上述四个消费方全在 Phase 2+，而 RAG 与自有网关同样在 Phase 2，因此本项在 MVP 内**唯一的消费方只剩 §4.3 的字段填充，且该字段在 MVP 阶段基本为空**。也就是说本项在 MVP 里**没有可演示的产出**——它是技术债预付，不是功能交付。
> 结论仍是做（理由不变），但必须提前向团队讲清这一点，否则第 2 周评审时它极易被当成"没做出东西"而被挤掉。**它不在任何砍单清单中，见 §4.10③。**

### 4.3 可配置 AI 上下文 schema

工单/日志/告警可携带的 AI 上下文字段改为**部署时配置**，而非硬编码：

### 4.5 三元身份绑定（取消 SSO 后的关键设计）

**问题**：没有通讯录同步，平台不知道企微群里发言的人对应哪个平台账号，也不知道 GitHub 上的 `@zhangsan` 是谁。**身份映射从"自动同步"变成"用户自助绑定"，这是取消 SSO 的直接代价。**

| 绑定项 | 方式 | 用途 |
|---|---|---|
| **企微 userid** | 用户私聊 `@Relay` 发送 `绑定`，机器人回验证码 → 用户在平台设置页输入 | 群内建单、通知触达、消息归属 |
| **GitHub handle** | GitHub OAuth 授权绑定（最可靠，无需手输） | 同步时的 @提及 翻译、PR 关联、责任人映射 |

**未绑定用户的降级行为**（必须明确定义，否则体验断裂）：

| 场景 | 行为 |
|---|---|
| 群内 `@Relay` 提问 | **允许**，问答不需要身份 —— ⏸ **但 MVP 无问答能力**（RAG 在 Phase 2），机器人回引导话术；Phase 2 起生效 |
| 群内 `@Relay` 建单 | **拒绝**，私聊引导绑定（工单必须有明确 reporter） |
| GitHub 同步遇未映射用户 | 保留为纯文本，**绝不误 @ 到无关 GitHub 用户**，并提示 Admin 补映射 —— ⏸ Phase 2（随 GitHub 同步） |
| 通知触达 | 降级为站内信 + 邮件 |

> **绑定项优先级**：GitHub 同步排在 Phase 2 后，**企微 userid 绑定是 MVP 硬前置**（机器人建单、通知触达、消息归属全靠它，且是 §4.11 的验收门槛）；**GitHub handle 绑定在 MVP 内价值有限**——其三项用途（@提及翻译、PR 关联、责任人映射）中只有「关联 PR」字段（§4.7）在 MVP 内存在，且 MVP 可退化为手工粘链接。因此 GitHub handle OAuth 绑定列为**可砍项**（§4.10③ 第 5 位），但**必须在 Phase 2 GitHub 同步开工前补齐**。

**运维风险提示**：无 SSO 意味着**离职/转岗不会自动停用账号**。MVP 阶段需建立管理员手动流程（建议接入 HR 离职流程 checklist），并在 Phase 2 补上企微 SSO 时一并解决。这条要写进运维手册，否则会成为安全审计的问题项。

### 4.6 日志（双模式 + 版本 + 分享 L0–L3）

MVP 范围如下：

**做**
- Markdown / 纯文本双模式，实时预览分屏
- GFM 全集 + 代码高亮 + Mermaid + 工单卡片内联 `#331`
- 自动保存、版本历史（保留 90 天）、diff 视图、任意版本回滚
- 附件与图片上传
- 分享 L0 私密 / L1 指定人 / L2 空间内 / L3 全组织
- 日志模板：日报、排查记录、故障复盘、设计文档
- 全文搜索
- **勾选「加入知识库」标记**（字段 + 勾选交互在 MVP，⏸ **向量化与 RAG 索引随 §4.9 排在 Phase 2**）
  > **为什么只保留标记、把索引放到 Phase 2**：这是全局里唯一一处刻意"半做"的功能。标记留在 MVP，团队在第 6–12 周写的日志就已经带上了"该不该进知识库"的人工判断；Phase 2 开索引时可**直接回溯全部历史日志**，无需组织一次二次标注。反之若连字段一起砍，Phase 2 冷启动（§4.9① 已列为该模块最大风险）会额外背上一轮全量人工标注。成本约 0.1 人·周，收益是消除一个 Phase 2 的启动阻塞——**因此列入不可砍项**（§4.10③）。

**不做（推迟至 Phase 2）**
- L4 外链分享与 DLP 扫描（外链是最大泄露面，MVP 不开）
- 多人实时协同编辑（CRDT 成本高；MVP 用编辑锁 + 冲突提示替代）
- `!trace:` / `!metric:` 内联语法（依赖 Gateway 侧集成）
- AI Copilot 撰写、日报自动生成

### 4.7 工单 + 看板（+ ⏸ GitHub 双向同步 v1 → Phase 2）

**工单 MVP 字段**
类型（Bug/Feature/Task）、标题、描述、状态、优先级 P0–P3、负责人、报告人、标签、迭代、关联 PR、评论。
Gateway 专属字段（tenant/provider/model/trace_id 等）**保留在数据模型中但 MVP 不做自动填充**——等 Phase 2 告警接入后才有数据源，提前做只是空字段。

**状态机（MVP 简化）**
`Todo → In Progress → In Review → Done`，外加 `Blocked` 与 `Won't Fix`。
完整状态机（含 Triage / Verifying / Reopened）推迟。

**视图**：列表 + 看板（按状态分组，支持拖拽）+ 我的工单。甘特与日历推迟。

**GitHub 双向同步 v1 —— ⏸ Phase 2（规格完整，不打折）**

> **为什么不进 MVP**：这是 Phase 1 全期的最高风险项（3 人·周，**唯一一个做砸就会让用户彻底不信任平台**的模块）。把它放在 MVP 硬性边界之外，**第 6 周的 MVP 是否成立就不再取决于同步是否做扎实**——这个解耦是范围划分最主要的收益。
>
> **排在 Phase 2 ≠ 降级，三条硬约束不变**：
> ① 下表中的**回环三防与双通道对账一项不能少**，在 Phase 2 内部仍是不可砍项；
> ② **先绑 1 个仓库灰度 2 周**再扩展全仓库；
> ③ 实施窗口按第 7–12 周安排（§4.10②），可拿到约 6 周灰度期。
>
> **MVP 阶段的连带影响**：
> - 工单的 `关联 PR` 字段在 MVP 内是**手工粘贴的链接字段**，无状态回传、无 CI/Review 状态；
> - 机器人建单流程第 ⑤ 步不同步 GitHub（§4.8③），工单只落在 Relay 内；
> - `relay-sync[bot]` 与 `relay:meta` 标记不会在 MVP 期间写入任何 Issue，**因此命名锁定的截止期是"Phase 2 同步开工前"**（§8.2）；
> - GitHub handle 绑定在 MVP 内价值有限（§4.5），但须在 Phase 2 开工前补齐。

同步设计如下，**回环三防与对账机制一项不能少**：

| 必做 | 说明 |
|---|---|
| GitHub App 授权 | 非 PAT；专用 Bot `relay-sync[bot]` |
| 字段映射 | 标题、正文、状态、负责人、标签、里程碑、评论 |
| **回环三防** | Actor 过滤 + rev 版本号 + 内容指纹，三者缺一不可 |
| **双通道** | Webhook 实时 + 5 分钟增量对账 + 每日全量对账 |
| **冲突处理** | 字段归属矩阵；冲突不静默丢弃，展示冲突条供人工选择 |
| 速率与降级 | 令牌桶 + 指数退避 + 死信队列可重放 |
| 同步可观测 | 延迟 P95、成功率、冲突数、单条工单同步时间线 |

**MVP 可以打折的部分**：附件转存、Projects v2 字段同步、`relay:meta` 折叠区块（Gateway 专属字段尚无数据，可暂不写入）。

> **强烈建议**：**先绑定 1 个仓库灰度运行 2 周**，确认同步稳定后再扩展到全部仓库。双向同步一旦出现数据错乱，用户的信任几乎无法挽回。
>
> **两项实施前必须定的事**：
> ① **状态映射有损**：本节的状态机有 6 个状态（`Todo / In Progress / In Review / Done / Blocked / Won't Fix`），而 GitHub Issue 只有 open/closed（+ labels / state_reason）。`In Review`、`Blocked`、`Won't Fix` 回同步时必须落到 label 或 state_reason，**是冲突与回环的高发区**。字段归属矩阵必须**显式写出状态的双向映射规则与冲突时的胜出方**，不能留给实现临场决定。
> ② **止血开关**：需提供一键把同步降为**单向（GitHub → Relay）或全量暂停**的开关。对账发现不一致时先止血、再修数据，避免错乱在两侧持续放大。

### 4.8 IM 机器人（群内建单 + 问答）

#### ① 触发方式：只做 `@Relay`，不做全群监听

**这是 MVP 最重要的边界判断。**

全群消息监听并自动判断"这是不是一个问题"，在 MVP 阶段的问题是：
- **误报代价高**：机器人在讨论中途插话，团队一周内就会把它静音，此后再难挽回
- **隐私顾虑**：全量读取群消息需要团队心理接受度，内部群也不例外
- **成本**：每条消息都过一次模型，成本与收益严重不匹配
- **无评测基线**：MVP 阶段没有数据判断"什么是问题"，准确率无从保证

**折中方案（推荐纳入 MVP）**：机器人被动监听但**不在群内发言**——检测到高置信度的问题描述时，**私聊提醒发言人**："刚才在 XX 群提到的问题，需要建个工单吗？" 一键建单。

这个设计的好处：零打扰、可积累"什么算问题"的标注数据（用户点了建单 = 正样本），为 Phase 2 的自动识别打基础。**若人力紧张，此项可砍，不影响 MVP 成立。**

#### ② MVP 机器人能力清单

| 指令 | 行为 | MVP |
|---|---|---|
| `@Relay 建单 <描述>` | 生成工单草稿卡片 → 确认/编辑/取消 → 创建 | ✅ |
| 引用某条消息 + `@Relay 建单` | 抓取被引用消息及上下文作为工单描述 | ✅ |
| `@Relay #331` | 返回工单状态卡片（状态、负责人、最近更新） | ✅ |
| `@Relay 绑定` | 私聊触发身份绑定流程 | ✅ |
| `@Relay <问题>` | RAG 问答，返回答案卡片 + 引用来源；低置信度拒答 | ⏸ **Phase 2**（随 §4.9） |
| 答案卡片上的 👎 + 一句话 | **纠错入口**，生成知识修订草稿（见 §4.9④） | ⏸ **Phase 2**（依附于答案卡片） |

> **MVP 阶段对未开放指令的回应必须明确，不能沉默。**
> 收到疑似提问（`@Relay` 后不带 `建单` / `#编号` / `绑定`）时，回固定引导话术：
> "问答能力还没开放（预计 Phase 2）。现在可以用 `@Relay 建单 <描述>` 建工单，或 `@Relay #编号` 查状态。"
> **顺带把这些提问记录下来**——它们是 Phase 2 知识种子的真实需求样本，也是 §4.9① 冷启动"该先导入什么"的最好依据。这项几乎零成本，但显著降低 Phase 2 的冷启动风险。

> **机器人的 LLM 调用在 MVP 阶段直连供应商**（"跑在自有网关上"在 Phase 2），因此 MVP 期间**拿不到按功能拆解的成本视图**。§7.1 第 5 条的成本上限仍需先定，且在无网关的情况下更需要一个硬性预算告警。

#### ③ 建单流程

```
@Relay 建单 <描述>  或  引用消息 + @Relay 建单
   ↓
① 身份校验 —— 未绑定则私聊引导，流程终止
   ↓
② 上下文抓取 —— 被引用消息 + 群内前后若干条
   ↓
③ AI 生成草稿 —— 标题、描述、类型、优先级建议
   ↓
④ 群内确认卡片 —— 【创建】【编辑】【取消】，5 分钟未响应自动失效
   ↓
⑤ 创建工单 →（⏸ Phase 2 起同步至 GitHub）→ 卡片原地更新为工单链接
```

**关键**：**永远不自动创建，必须确认**。工单是有 owner 和 SLA 的实体，误建的成本远高于少建。

> **第 ③ 步是 MVP 唯一的 AI 价值证明点。**
> RAG 问答在 Phase 2，"AI 生成草稿"（标题、描述、类型、优先级建议）是团队在 MVP 阶段唯一能直接感受到 AI 的地方。因此它的验收指标——**草稿确认率 > 60%（未大幅编辑即创建）**——从体验指标升级为**不可打折的硬指标**（§4.11）。见 §0.3 判断五。
> 实施提示：草稿质量主要取决于第 ② 步的上下文抓取范围。建议把"抓取了哪些消息"在确认卡片上**可见且可调**（如"已包含前 5 条"→ 可展开到 10 条），比调 prompt 见效更快。

#### ④ 通知（MVP 范围）

工单指派、@提及、状态变更 → 企微应用消息；聚合窗口 5 分钟防轰炸。
分级路由、免打扰时段、订阅规则推迟至 Phase 2。

### 4.9 RAG 问答引擎 —— ⏸ Phase 2（规格完整保留）

> **为什么不进 MVP**：4 人·周（引擎 3 + 知识种子 1），是移出 MVP 的三项中最大的一块。代价已在 §0.3 判断五与 §4.0 明示——**MVP 的 AI 价值只剩建单草稿**，这条风险被接受而非消除。
>
> **排在 Phase 2 ≠ 降级，三项在 Phase 2 内仍是不可砍项**：
> ① **知识种子 ≥100 条的上线硬门槛**（① 冷启动）；
> ② **纠错入口**（④，知识飞轮的起点）；
> ③ **强制引用 + 拒答优先**（②③，首次上线阶段控制错答率的唯一手段）。
>
> **MVP 阶段为本模块预付的两件事（都很便宜，但能显著降低冷启动风险）**：
> - 日志的**「加入知识库」勾选字段保留**（§4.6）——Phase 2 开索引时可回溯全部历史日志，不用二次标注；
> - 机器人**记录所有被拒的疑似提问**（§4.8②）——这是"该先导入什么知识"的真实需求样本，比凭空猜测的导入清单准得多。
>
> **本节以下是本模块的完整规格**，实施时间为 Phase 2；文中"MVP"一律读作"本模块首次上线"。

#### ① 冷启动是本模块最大风险

> **一个没有种子知识的 RAG 机器人，第一周会一直回答"我不知道"，团队会在它变好之前就放弃它。**

因此 **知识种子导入必须排在问答能力开放之前，而非之后**：

| 种子来源 | 预估量 | 优先级 |
|---|---|---|
| 现有文档导出（Confluence / Notion / 飞书） | 大 | P0 |
| GitHub 仓库 `docs/`、README、CHANGELOG | 中 | P0 |
| **错误码表 / OpenAPI spec** | 小但高价值 | P0（答疑命中率最高的一类） |
| 历史已关闭工单（批量萃取 FAQ 草稿） | 大 | P1 |

**硬性门槛：知识条目 ≥ 100 条方可对团队开放问答能力。** 达不到就继续导入，不要提前发布。

> **提示**：这条门槛约束的是**机器人的问答指令**，而非机器人本身——机器人在 MVP 阶段已带着建单与状态查询上线。好处是**冷启动不是"上线即失败"的一次性赌注**：问答能力可以在知识达标后单独开放，届时团队对机器人的信任已由建单功能先建立起来。这是把 RAG 放在 Phase 2 的一个附带收益。

#### ② 检索与生成（MVP 简化）

- **切片**：按 Markdown 标题层级切分 + 固定重叠，保留标题路径作为上下文
- **检索**：BM25 + 向量混合召回；MVP **不引入 rerank 模型**，用召回分数加权即可
- **生成**：**强制引用**，每个论断附来源链接；证据不足时明确拒答
- **元数据**：MVP 只做 `module`、`scope`、`owner`、`updated_at` 四个字段；权威分级、版本区间、有效期推迟

#### ③ 拒答优于乱答

MVP 阶段知识稀疏，拒答会很频繁，这是**正常且正确的**。拒答话术要给出下一步："这个问题知识库暂无覆盖，我已记录为知识缺口（#412），你可以 @张三 或直接建单。"

#### ④ 纠错入口（本模块首批必做，不可推迟）

答案卡片上的 👎 + 一句话纠正 → 生成知识修订草稿 → 推送给 owner 确认 → 生效。

**这是知识飞轮的起点，必须与问答能力同批上线。** 完整的冲突检测、回归验证、灰度生效推迟至 Phase 3，但"看到错答案能顺手改"这个动作必须在问答开放的第一天就在。

> 本项随 RAG 一同排在 Phase 2，但**在 Phase 2 内部是不可砍项**——砍掉则知识永不更新，飞轮转不起来。

#### ⑤ 三阶段演进在本模块的例外

机器人原则上须走「影子 → 副驾驶 → 自动」三阶段。**但问答能力首次上线时（Phase 2）允许在内部群直接回答**，理由：

1. 仅限**内部群**，容错高，不面向任何外部客户
2. 强制引用 + 拒答优先，错误可被立即识别
3. 影子模式需要人力持续标注，此阶段没有这个人力
4. 上线后的问答数据本身就在积累评测集
5. MVP 期间机器人记录的被拒提问（§4.8②）已经提供了一批真实问题样本，可作为上线前的最小自测集——这部分弥补了没有影子模式的缺口

> **但三阶段演进对外部客户群依然是硬性要求，不因上述调整而放宽。** 这条边界不能模糊。

> ⚠️ **入站脱敏：MVP 期间没有风险窗口，但 Phase 2 有硬性顺序约束。**
> §2.6 指出"不脱敏就入库，等于把泄露风险永久固化进检索层"，而完整 AI-DLP 排在 Phase 2。MVP 阶段没有向量库，因此没有可被固化的风险；**代价是 Phase 2 里 RAG 与 DLP 入站方向的相对顺序成为硬约束**：**入站脱敏必须先于或同批于首次知识入库**。至少要有最小过滤（正则 + 熵值检测：API Key / Token / 内网 IP / 手机号），命中即阻断入库并告警。完整 DLP 可以慢慢做，但不可逆的那一段不能等。

#### ② 12 周两里程碑

**里程碑 A（第 1–6 周）· ★ MVP 硬性验收边界 —— 内部可用**（≈ 11 人·周）

| 周次 | 内容 |
|---|---|
| 第 1–2 周 | **多租户数据模型 + 遥测适配器接口**（必须最先，见下方警告） |

> 两个架构性前置项必须排在**最前面**，而非并行插入。`tenant_id` 一旦漏进任何一张表，后面每写一个模块都在放大返工面。建议配套一条 **migration lint**（新建表必带 `tenant_id`），机械保证，不依赖 code review。

> **里程碑 A 就是 MVP 的验收边界。** 这里的内容全部不含高风险项，因此第 6 周的交付是**确定性的**。§4.11 的 MVP 验收指标全部在此判定。

**里程碑 B（第 7–12 周）· MVP 完成 + 转入 Phase 2**（≈ 9.5 人·周）

| 优先级 | 内容 | 身份 |
|---|---|---|
| 1 | **企微机器人**（群内建单 + AI 草稿 + 状态查询 + 绑定）+ **企微应用消息通知** | MVP 收尾（2 人·周 + 联调 0.5） |
| 2 | **GitHub 双向同步 v1**（单仓库灰度，回环三防 + 双通道对账） | ⏸ Phase 2 提前开工（3 人·周） |
| 3 | **RAG 引擎 + 知识种子导入**（≥100 条门槛 + 纠错入口） | ⏸ Phase 2 提前开工（4 人·周） |

→ *正式停用 Jira*（判定只依赖优先级 1 与里程碑 A，**不依赖优先级 2/3 的完成度**）

> **优先级 2 与 3 的顺序是可调的，且应在里程碑 A 复盘时带着真实反馈重新判断。**
> 默认顺序（先同步、后 RAG）的理由是同步风险更高、需要更长灰度期。
> **但若第 6 周的双轨试用反馈是"感觉就是个 Jira"**（§0.3 判断五预警的情形），应把 RAG 提到第一位——那说明 AI 价值的缺失已经在真实伤害采纳率，而 §4.0 论证过，这是比同步延期更严重的失败模式。

> 分两个里程碑的价值：第 6 周就能拿到真实反馈，而不是等 12 周后一次性验证。MVP 的成立条件全部收在里程碑 A 内，使"MVP 能否交付"与"高风险项能否做扎实"两件事**互不牵连**。

> 里程碑 A 只有 11 人·周 / 6 周，**已有约 4 周冗余，这份清单大概率用不到**。写下它是为了万一里程碑 A 出现意外时有既定顺序，不必临场争论。

| 顺序 | 砍什么 | 影响 |

| 2 | 日志模板（保留自由格式） | 体验略降 |
| 3 | 看板拖拽（保留列表 + 状态下拉） | 体验降，PM 会有意见 |
| 4 | 工单 `#331` 状态查询指令 | 少一个便利入口 |
| 5 | **GitHub handle OAuth 绑定** | MVP 内价值有限（GitHub 同步在 Phase 2，见 §4.5）；**但必须在 Phase 2 同步开工前补齐** |
| 6 | 可配置 AI 上下文 schema 的 UI 显隐配置（保留数据模型字段） | 无——字段在 MVP 阶段本就是空的（§4.3） |

| **不可砍** | **遥测适配器接口** | 不抽象则 Phase 2 有四处返工；即便 MVP 内看不到产出也不能砍 |
| **不可砍** | **企微 userid 绑定** | 砍掉则机器人整体不可用（建单、通知、消息归属全依赖它） |

| **不可砍** | **日志「加入知识库」标记字段** | 约 0.1 人·周；砍掉则 Phase 2 开索引需组织一轮全量人工标注（§4.6） |

| 不可砍 | 理由 |
|---|---|
| **GitHub 同步的回环三防与双通道对账** | 砍掉必翻车，用户信任无法挽回 |

### 4.11 验收标准

#### ① MVP 验收（里程碑 A 第 6 周 + 里程碑 B 优先级 1）

| 类别 | 指标 | 目标 | 判定点 |
|---|---|---|---|
| **安全（硬门槛）** | 跨租户越权读写 | **0** —— CI 门禁必须常绿，上线前一次渗透抽测 | 里程碑 A |
| **底座（硬门槛）** | 企微 userid 身份绑定率 | **> 90%** —— 机器人可用性的天花板，见 §0.3 判断三 | 里程碑 A 末 |
| **采纳（硬门槛）** | Jira 停用 | **100%**，连续 2 周全部工单在 Relay 流转 | 里程碑 B |
| 采纳 | 周活跃创作者占比 | > 70%（MVP 阶段目标低于长期 80%） | 里程碑 B |
| 机器人 | 群内建单占新建工单比例 | > 20% | 里程碑 B |
| **机器人（硬门槛）** | 建单草稿确认率（未大幅编辑即创建） | **> 60%** —— **MVP 唯一的 AI 价值证明点，不可打折**（§0.3 判断五） | 里程碑 B |
| 底座 | 日志「加入知识库」勾选覆盖率 | 有意义的正样本 ≥ 30 篇（为 Phase 2 冷启动预热，§4.6） | 里程碑 B |
| 底座 | 机器人记录的被拒提问数 | ≥ 50 条（Phase 2 知识种子的需求样本，§4.8②） | 里程碑 B |

> **MVP 的三项硬门槛**——跨租户越权 0、身份绑定率 >90%、Jira 停用 100%——特征是**都不依赖任何高风险项**，与"里程碑 A 是确定性交付"的设计一致。知识 ≥100 条、同步冲突率 <1%、问答错答率 <5% 三项随对应模块归入 §4.11②。
>
> ⚠️ **指标口径必须先定，否则可被少数人刷高**：「周活跃创作者占比」与「群内建单占比」都需明确**分母**（团队在册人数 vs 已绑定人数；统计窗口为自然周）。建议在里程碑 A 期间就把口径写进看板，而不是验收前临时对齐。

#### ② ⏸ Phase 2 项的验收项（指标与目标不打折）

| 类别 | 指标 | 目标 |
|---|---|---|
| **同步** | GitHub 同步 P95 延迟 | < 30s（首次上线放宽，长期目标 10s） |
| **同步（硬门槛）** | 同步冲突率 / 数据不一致率 | **< 1% / < 0.1%** |
| **同步** | 对账发现的漏同步 | 每周 < 5 条且全部可自动修复 |
| **问答** | 首答命中率 | > 40%（知识稀疏，目标刻意放低） |
| **问答（硬门槛）** | **错答率**（给出答案但错误） | **< 5%** |
| **问答** | 拒答时给出了有效下一步 | 100% |
| **知识（硬门槛）** | 问答开放时的知识条目数 | **≥ 100** |
| **知识** | 首月纠错触发次数 | > 20（验证飞轮起转） |

> **首答命中率目标刻意定在 40%**：知识稀疏阶段追求高命中率会诱导降低拒答门槛，进而推高错答率——**那是更坏的结果**。这个阶段要盯的是错答率和纠错次数，而不是命中率。
>
> ⚠️ **错答率 <5% 目前没有度量手段。** 它是一票否决级指标，但 AI 评测体系排在 Phase 3。开放问答前必须先有最轻量的度量：**问答日志留存 + 每周人工抽样复核 N 条 + 把 👎 计入分母**。否则验收时这一格无法填，指标形同不存在。

> **三条依赖关系不可打破：**
> ① **Tier 2 前置**（见 §2.2⑦）：M0 变更管理与 On-call 排班已上线、Tier 1 稳定运行 ≥1 个月且解析准确率 >95%、完成红队演练。因此 M0 底座已在 Phase 2 并行排入，不可推迟。
> ② **三阶段演进**：问答能力首次上线（Phase 2）允许机器人在**内部群**直接回答（见 §4.9⑤），但面向**外部客户群**时必须完整走影子 → 副驾驶 → 自动，这条边界不因任何范围调整而放宽。
>
> ③ **Phase 2 三项的质量要求不因排期靠后而放宽**：GitHub 同步的回环三防与对账、知识种子 ≥100 条门槛、纠错入口，在 Phase 2 内部依然是不可砍项（§4.10③）。排期靠后只改交付时点，不改质量要求。

## 8. 产品命名：Relay

### 8.1 命名依据

**Relay 精确命名了本产品要解决的那个失败。** 整份 PRD 的核心命题是上下文断裂——告警到群聊断一次、群聊到工单断一次、值班交接再断一次。Relay 即"接力/交接"，而交接失败正是 on-call 场景最痛的问题。名字与问题同构，不需要额外解释。

定位扩展至 AI Native 团队后，这个名字**依然成立且更通用**：AI Gateway 本身是一个 relay，一次顺畅的 on-call 交接也是；两者的失败方式相同——**在传递途中丢掉上下文**。

四条支撑理由：

| 维度 | 说明 |
|---|---|
| **语义共享** | AI Gateway 本身就是 relay（转发、路由、中继）。内部人一听即懂为什么叫这个，名字自带论证 |
| **呼格质量** | 本产品每天被"呼叫"数十次（`@Relay 查一下延迟`）。两音节、中英混说自然、输入法友好 |
| **动词而非容器** | 老一代协作工具用容器隐喻（Hub/Base/Space/Center），因为它们是存放处；Relay 会自己动——自动建单、自动答疑、自动补知识，是执行者 |
| **不含 AI 后缀** | AI 是本产品的基底而非卖点。XxxAI / XxxGPT / XxxBot 类命名会快速过时 |

### 8.2 命名规范（全链路统一）

| 场景 | 规范 | 示例 |
|---|---|---|
| 产品全称 | Relay | Relay · AI Gateway 内部协作平台 |
| IM 机器人 | `@Relay` | `@Relay 查一下 azure 延迟` |
| GitHub 同步 Bot | `relay-sync[bot]` | 用于回环识别与审计，见 §4.7 |
| Issue 元数据标记 | `<!-- relay:meta:start -->` | 见 §4.7 |
| 内部域名 | `relay.internal` | 工单链接 `https://relay.internal/t/331` |
| 工单前缀 | `RL-` | `RL-331`，用于 PR 描述与分支名自动关联 |
| MCP Server | `relay-mcp` | IDE / Claude Code 接入标识 |

> **注意**：`relay-sync[bot]` 与 `relay:meta` 标记一旦上线即写入 GitHub Issue 正文，**后续改名需要数据迁移**（重写历史 Issue 的元数据块 + 更新 SyncMapping）。
>
> GitHub 同步在 Phase 2，MVP 期间不会有任何 Issue 被写入元数据块，**因此这两个名字的锁定截止期是"GitHub 同步开工前"**（即里程碑 B 优先级 2 启动之前）。
> 但仍**建议在 Phase 1 内完成锁定**：产品全称、`@Relay` 呼叫名、`relay.internal` 域名、`RL-` 工单前缀在 MVP 阶段就已对团队可见，改名的沟通成本本身也不低。§8.3 的商标检索也应在此窗口内完成。

### 8.3 遗留事项

1. **商标与同名检索未完成。** Relay 是常用词，大概率存在同名软件项目。若纯内部使用则无影响；**若采纳对外商业化路径（见 §7 待决策第 2、7 条），须先完成商标检索、域名可得性与跨语言歧义检查。**
2. **中文名待定。** 本平台主要在企微生态中使用，团队以中文交流，中文机器人名（如"接力"）在群内可能比英文更顺口。建议在 Phase 1 灰度期间实际观察团队呼叫习惯后再定，不必现在决策。
