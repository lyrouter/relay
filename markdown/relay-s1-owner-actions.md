## 阻塞项

### B-1 下一步做什么：Web UI 的 HTTP 层没有任务

**是什么**。weeks 3–6 剩下的全是前端：LOG-1/2/3/7 与 TKT-5/6/7/9，共 13 pd。
一行都动不了——`src/relay/api/` 是空的，没有任何 HTTP 端点可以调。

计划里**没有**「Web UI 自己的 HTTP 层」这个任务。API-1/2/3 覆盖的是**对外**工单
API（token 鉴权、`/api/v1`、幂等、webhook）；Web UI 另外还需要会话登录、日志读写、
通知已读、附件上链接这些端点。设计 §8.1 要求它们都走现有 use case，不能绕过去
——所以这不是「前端顺手写个后端」，而是一块没被拆出来的活。

**为什么必须你定**。这是范围问题：它要么算进 S1（那 57.5 pd 的估算少了一块），
要么把前端推到第 7 周之后。我不该自己替你把 20 个端点的范围定下来。

**我的建议**：先做 HTTP 层，顺序是
① API-5 的 RFC 9457 错误处理器 + 会话依赖（每条路由都要用，先立规矩）
→ ② Web UI 需要的读写路由
→ ③ API-1/2/3 的对外 `/api/v1`。
这一块大约 3–4 pd，做完前端才有东西可接。**理由**：错误格式和鉴权依赖如果最后补，
每条路由都要回头改一遍；而且 MT-6 剩下的那一半（「A 租户的 token 拿 B 租户资源
要 404 而不是 403」）本来就卡在 API-1 上，做了这块它才能关闭。

**要你回一句**：按这个顺序做 HTTP 层，还是先搭 Vue 骨架、端点先 stub 掉。

## 需要改设计文档的决策

### D-1 确认 Admin 能读别人的私密日志（L0）

**是什么**。设计里有两句话冲突：

- §5.4 角色表：Admin 的「查看内容」是 **按分享级别**，和 Member 同一行；
- §6.3 分享表：**L0 私密 = 仅作者 + Admin**。

我按 **§6.3** 实现了（更具体的胜），也就是：**Admin 能读任何人的私密日志**，
而且因为 L0 是最严的一级，这必然意味着 Admin 能读所有级别——否则「Admin 看得到
私密日志但看不到空间共享日志」这个顺序讲不通。

**为什么必须你确认**。这是隐私决策，不是笔误级别的取舍。它的后果是：管理员账号
= 全租户阅读权限。而 AC-1 之后账号不是 Admin 一个个发的，Admin 自己可能都不知道
有谁在——所以这条和「谁能当 Admin」是绑在一起的。

**还有一件必须一起定的事**：**Admin 读私密日志现在不留审计行。** 审计只记写入和
分享级别变更（`log.created` / `log.share_level_changed` / `log.share_granted` …），
读取一行都不记。也就是说这条权限目前**只能靠信任角色，没法事后复核**——对一个
「管理员可以看所有人私密草稿」的决策来说，这是缺了一半。

**我的建议**：**保留现在的实现（Admin 可读）+ 补上读审计**，并且**把 §5.4 那一行
改成指向 §6.3**，别留着两句话打架。理由：设计已经明确写了 L0 = 仅作者 + Admin，
实现跟着更具体的那句走；但「有这个权限」和「用了这个权限有痕迹」应该一起成立——
没有痕迹的全租户阅读权限，在真出事的时候是查不动的。补读审计约 0.5 pd，只记
「Admin 读了不属于自己的 L0/L1/L2 日志」这一种情况，不记普通读取（否则审计表会被
正常浏览刷满，真正要看的那几行反而埋掉了）。

**如果你要反过来**（Admin 不能读 L0）：改 §6.3 那一行，我改
`relay/domain/permissions.py` 的表 + 三个测试，半天以内。这样也就不需要读审计了。

> ⚠️ 我上一轮汇报时说过「Admin 不是 super-reader」，那句是错的——依据的是 §5.4
> 而漏了 §6.3。代码、测试和三处文档已经改正，这条列在这里是让你**确认结论**，
> 不是让你再看一遍我的更正。

### D-2 定时任务用什么身份跑（90 天清理现在跑不起来）

**是什么**。LOG-4 的 90 天版本清理（S-8）已经实现（`app/logs/retention.py`），
但它要求 `USER_MANAGE`，也就是**要有一个活着的 Admin 用户在 TenantContext 里**。
定时任务没有会话、没有用户——所以这个清理**现在没法被调度**。

**为什么必须你定**。可选路径有三条，选哪条是架构决定：
① 让定时任务「扮演」某个 Admin —— 最省事，但审计行会记到一个没在操作的人头上；
② 走 `SystemRepository`（BYPASSRLS + 每次调用写审计） —— 语义正确，但清理是
按租户跑的，用跨租户通道做租户内的事有点重；
③ 给 `TenantContext` 加一个「系统执行者」身份（`ActorType.SYSTEM` 已经有了，
缺的是让 `actor_principal` 接受它并要求一个显式能力）。

**我的建议**：**③**。`ActorType.SYSTEM` 这个枚举值本来就存在且现在没人用，
让调度器带着它进来、审计行如实记成 system，比借一个人的身份干净。大约 0.5 pd，
包含一条「系统身份不能用来服务 HTTP 请求」的测试。

**最晚什么时候**：自动保存每次都写版本，所以版本表长得快。团队开始认真写日志之后
两个月内要能跑起来，否则第一次清理会一次删掉很多行。

### D-3 T-2 · 访客能不能看到整个工单看板

**是什么**。现在**能**。工单没有分享级别字段，等于天生 L3（全租户可见），
所以 Guest 能看到看板上所有工单。§5.4 里「查看内容: 按分享级别」那一行是照日志
写的，工单没有对应机制。

**为什么必须你定**。给工单加 per-ticket ACL = 加一列 + 定一套判定顺序，
是设计决策不是实现细节。而且它和 Guest 这个角色存在的理由直接相关：Guest 是给
外部承包商用的，让承包商看到整个看板通常不是本意。

**我的建议**：**S1 保持全租户可见，但写进手册**——「不要把 Guest 账号发给不该看
到看板的人」——然后等 LOG-6 的判定顺序摆在眼前时一起重新看。理由：S1 是内部团队
双轨试用，工单本来就是团队内公开的；而临时加一列 ACL 会让 §8 的 API 响应也要跟着
变，那是发布即冻结的东西。

**最晚什么时候**：**第一个 Guest 账号创建之前**。不是第 7 周——是谁第一次点
「邀请一个访客」之前。

### D-4 F-6 · 反馈链路的三个产品细节

**是什么**。计划里原有的遗留项，我没动它。三个问题：网关 WebUI 要不要显示处理
进度、谁通知提交人、反馈默认字段。

**我的建议**（和 TODO-S1 里记的一致）：① WebUI **显示**进度，靠轮询
`GET /tickets/{key}`，只给状态和最后更新时间，**绝不给内部评论**；② **由 WebUI**
通知提交人，不是 Relay——Relay 直接触达网关用户就变成对外系统了，那是 Phase 4；
③ 反馈默认 `type=Bug, priority=P2`，由 assignee 分诊，**不让提交人选优先级**，
否则一周内全是 P0。

**最晚什么时候**：第 5 周，API-6 开工前。

> ⚠️ 决定这条整合值不值的**不是技术**：**反馈提了没人回，就没人会提第二次。**
> ①② 就是为了闭上这个环。

### D-5 T-1 · 状态机缺两条流转

**是什么**。§7.2 画的图里没有这两条边，我**没有**擅自加：

① **`Done → Todo`**（重开）——修完发现没修好。§7.2 给 Won't Fix 明确写了可重开回
Todo，对 Done 什么都没说，而 `Reopened` 状态是明确推迟的。没有这条边，人只能新建
一个重复工单——那正是 INT-8 的计数看不穿的东西。
② **`In Review → In Progress`**（评审打回）——用 Blocked 表达是错的，Blocked 是
「等别的东西」，不是「被打回」。

**为什么必须你定**。状态取值和流转都会出现在 API 响应和 webhook payload 里，
改名/改图对外部系统是破坏性变更（§8.6）。悄悄加一条边等于改了没人评审过的契约。

**我的建议**：**两条都加**。两条都不需要新状态，所以冻结的枚举一个字都不用动；
同时在 §7.2 里补一句「重开保留原编号与 rev 历史」。

**怎么落地**：现在有两个测试**钉住了它们不存在**
（`test_ticket_state_machine.py::test_done_is_terminal_in_s1` 和
`::test_a_review_cannot_send_work_back_yet`）。加边会让这两个测试失败——这是设计
好的机制，不是障碍：它逼着改动的人先去改设计文档。

**最晚什么时候**：第 7 周，双轨试用把真实工单推到 Done 之前。

## 运维与环境

### O-1 `RELAY_BLOB_SIGNING_KEY` 必须设置

附件下载链接是 HMAC 签名的短时链接（S-11，5 分钟）。默认值故意写成
`dev-only-unsafe-signing-key`，这样**没设置的时候在配置评审里看得见**，而不是藏在
一个能用的链接后面。任何部署环境都要换掉。

同时确认 `RELAY_BLOB_ROOT` 指向的目录在备份范围内（见 O-5）。

### O-2 SMTP 发信通道要真的接上

F-5 已经确认「事务性发信通道存在」，代码这边 `MailPort` 也接好了——但
`RELAY_SMTP_HOST` 默认是空的，空 = `NullMailPort`，**信只记录不发出**。

影响的是三条路：邮箱验证（AC-1，**没有它没人能登录**）、异地登录告警（AC-2）、
邀请链接（AC-1 次要路径）。注意这三条都是**事务性邮件**，和 F-1「S1 通知只做站内
信」不冲突——F-1 管的是通知，不是这些。

**最晚什么时候**：第一个人注册之前。

### O-3 生产库装 pgroonga，并确认 PostgreSQL ≥ 15

- **pgroonga**：不是 trusted extension，要 superuser 装
  （`scripts/bootstrap_extensions.sql`）。LOG-8 的全文检索和
  `migrations/…_log_8_pgroonga_full_text_indexes.py` 都依赖它；迁移会在缺失时**直接
  报错并给出装法**，不会静默跳过。CI 和 dev 已经有了，生产要单独做。
- **PostgreSQL ≥ 15**：11 个外键用了 `ON DELETE SET NULL (column)`（S-18），
  14 上迁移直接失败。有测试会在版本不够时明确报出原因。

### O-4 第一个租户的 bootstrap 要写进部署手册

AC-9 决定的是**带凭据的一次性初始化**，不是「第一个注册的人变 Admin」。命令：

```bash
RELAY_BOOTSTRAP_PASSWORD=... uv run python scripts/bootstrap_tenant.py \
    --tenant-name "AI 网关团队" --tenant-slug gateway \
    --admin-email <admin@your-domain> \
    --domain-scope gateway
```

三件要写进手册的事：

1. **`--tenant-slug` 发布即冻结**（S-12）——它出现在每一个永久链接里
   （`https://relay.internal/{tenant_slug}/t/331`）。
2. **`--domain-scope gateway` 只给网关团队这一个租户。** 它开启 TKT-2 的
   `gateway_version` / `routing_policy` 两个字段。默认不开，是为了让第二个租户
   不会悄悄继承——§7.3 的判据是「没有自有网关的团队能不能给这个字段填出值」，
   答案要一直是「不能」。
3. 密码走环境变量或交互输入，**不要放命令行参数**（会进 shell history 和进程表）。
   脚本按 slug 幂等，重跑不会造出第二个 Admin。

### O-5 MinIO 要有个真实实例

LOG-5 的应用层做完了（大小/类型限制、病毒扫描位、key 里带 `tenant_id`、
先鉴权再签 5 分钟链接），但**MinIO/S3 适配器没写**——我故意没有盲写：没有真实
MinIO 可测的适配器，比一个明确缺失的适配器更糟。

需要你/运维给的：实例地址、access key、bucket 名、以及**备份口径**。

> ⚠️ **INT-11 的恢复演练必须同时覆盖 PostgreSQL 和 MinIO。** 只恢复数据库的结果
> 是「文字都在、每张图都碎」——而这种半恢复如果没在演练里出现过，就会在真实事故里
> 出现。

**最晚什么时候**：第 5 周。给了我地址我就把适配器补上（约 0.5 pd，key 布局不变，
所以不需要搬任何对象）。

## 流程与人

### P-1 R-2 每月账号复核 + 离职 checklist

没有 SSO，**离职/转岗不会自动停用账号**；自助注册让这条更重要，因为账号不是
Admin 一个个发出去的，Admin 未必知道有谁在。

已认领：**WANGLI**。要落地的两件事：① 每月一次账号复核；② 把「在 Relay 停用账号」
加进离职 checklist。

代码这边支持得上：`AdminService.deactivate_user()` 会**同时终止该用户所有会话**
并留审计行——停用不是只改一个状态位。另外「租户内最后一个 Admin」不能被停用也不能
被降级，因为 bootstrap 拒绝加第二个 Admin，那扇门关上就没法从产品里打开。

### P-2 AI 角色在 S1 无事可做

计划里原有的风险，不是我发现的：S1 没有 BOT、没有 RAG、没有网关路由，**AI 这个角色
整个 S1 没有活**。要么早点给 RAG 的分块/检索预研，要么并进 API/前端。让它空到 BOT
开工，会让 BOT 的 10 pd 看起来像凭空出现。

### P-3 双轨试用的观察项：通知看不见就开邮件

F-1 只做站内信有一个必须正视的后果：**站内信要求人主动进平台才看得到**。所以 S1
的采纳形态只能是「团队每天会打开 Relay」，不是「Relay 会来找人」。

**这条后果是可消除的**：发信通道存在（F-5），聚合窗口和投递状态机现在就按多渠道
建好了，**补上邮件通知约 0.5 pd**（NT-3）。

**要你做的**：把「通知触达」写进双轨试用的观察项。如果第 6 周的反馈是「我从来没
看见通知」，最便宜的解法是**打开邮件通知，而不是等 BOT**——否则团队会一边忍受触达
不足，一边等一个还有 4 周才到的机器人。

### P-4 LOG-9 验收前人工抽检 10 篇

S-16 定的计数口径是**勾选 + 正文 ≥ 300 字符**自动计入，代码里是
`KNOWLEDGE_MIN_BODY`，和 INT-8 看板用同一个常数所以不会打架。

口径之外的那一半是人的：**验收前抽检 10 篇**确认质量。这条要在验收会**之前**做，
不是会上临时对齐。
