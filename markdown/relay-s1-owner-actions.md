## 1. 已决策的事项（结论与落点）

### O-5 → S-25 · MinIO 适配器按标准 S3 盲写

**你的答复**：先按你的理解开发，后期有问题再开 BUG 修复。
**这一轮已按此实现**——三件都交付了，见下表末尾。

**结论**：**不再等实例信息**。适配器按**标准 S3 语义**写（S3 兼容客户端 + MinIO 的
path-style 寻址），载体由配置选择，`FilesystemBlobStore` 留给开发与测试。运维原本要给的
四样东西，前三样——地址 / access key 与 secret / bucket 名——**从「代码阻塞」变成「部署
配置」**，落在 [部署文档 §O-5](relay-s1-deploy.md#o-5-minio)；第四样**备份口径按 R-1 的建议
值执行**（每日增量同步到另一台主机，保留 30 天），你不另定就是它。真实实例上出现的偏差
按 **BUG** 处理，挂在 LOG-5 名下。

**盲写的边界要先说清**：盲写能写对的是**接口与语义**（key 布局、5 分钟预签、大小限制、
错误映射）；盲写写不对的是**部署形态**。所以这条不是「写完就算」，而是三件一起做——
后两件正是把「盲」缩到只剩部署形态的办法：

| 做什么 | 为什么它不能省 | 状态 |
|---|---|---|
| S3 适配器（`MinioBlobStore`），载体在装配处按配置切换 | 主体。key 布局与 `FilesystemBlobStore` 完全一致，所以换载体**不搬任何对象、不改任何已存的 `blob_key`** | ✅ `src/relay/infra/blob/minio.py`；开关在 `relay.api.wiring`，选 MinIO 时 `/blobs/{key}` 整条路由不挂载 |
| **容器化契约测试**：用 `minio/minio` 起一个真实服务，跑同一套 blob 契约 | 没有真实实例时，这是唯一能验证适配器的方式。它验证不了生产的网络与证书，但能验证语义 | ✅ `tests/test_blob_contract.py`，两个载体跑同一套契约；CI 里设 `RELAY_REQUIRE_MINIO_CONTRACT=1`，**跳过就是失败**（盲写的适配器最怕契约测试悄悄不跑了） |
| **冒烟脚本** `scripts/check_blob_store.py`：put → 预签 → GET → delete 一个往返 | 让真实实例**第一天就自证**。否则偏差的第一现场是产品里图片全裂，而那时已经在上线窗口里 | ✅ 已交付，退出码非 0 可直接进发布脚本；四处盲区一次验掉（签名 host · 寻址风格 · 时钟差 · bucket 是否私有） |

**代价说清**：LOG-5 从 **1 pd 变 1.5 pd**（适配器 0.5 在原估内，容器契约测试与冒烟脚本
0.5 是新增），S1 **61.5 → 62 pd**。这 0.5 就是盲写的价钱，我建议买下来：不买的话，
适配器第一次见到真实 MinIO 的时刻就是上线前那一晚。

**第一个 BUG 大概率落在这四处**。写出来，是为了让它被认出是**已知项**而不是谜案——
其中 ①②④ 冒烟脚本会直接报出来，③ 它会算出两端时钟差多少：

| # | 盲区 | 症状 |
|---|---|---|
| 1 | **预签名 URL 的 host**。MinIO 常见形态是「内网 endpoint + 反代域名」，签名用的 host 浏览器访问不到 | **图片全裂，而应用日志里什么都没有**——浏览器直连对象存储，请求根本不回到应用。解法是公网端点单独配一项，而不是复用连接端点 |
| 2 | **path-style vs virtual-host 寻址**。MinIO 基本只吃 path-style，SDK 默认可能是 virtual-host | `NoSuchBucket`，或者一个把 bucket 名当子域名去解析的 DNS 失败 |
| 3 | **时钟偏移**。预签名有效期只有 5 分钟，两端差几分钟就等于「链接一发出就过期」 | 「刚生成的链接说已过期」。两端都要 NTP，这条要写进部署清单 |
| 4 | **bucket 由谁创建、是否匿名可读** | 匿名可读会让 S-11 那套「先鉴权、再签 5 分钟链接」**整套白做**——bucket 必须私有 |

另有两处是**语义**而不是部署形态，我会在适配器里显式对齐，不留给运行时去发现：

- **大小限制的时机**。现在的 `BlobTooLarge` 是**流式判定**（超限只花掉一个 chunk）。S3 的
  multipart 上传要保持这个语义，否则 25 MiB 限制会退化成「先把文件收完再拒绝」——限制还在，
  但它保护不了带宽和磁盘。
- **`/blobs/{key}` 这条路由**。它依赖文件系统载体独有的 `verify` / `open`，MinIO 载体下没有
  对应物。所以载体切换**必须在装配处可见**：换成 MinIO 时这条路由要么下线、要么显式改成代理，
  不能留一个调用下去就 `AttributeError` 的入口。

⚠️ **盲写消不掉的两件事**（S-25 没有把 O-5 整个关掉）：

1. **真实实例仍然要存在。** 它现在是部署清单上的一行配置，不是代码阻塞——但上线前必须有，
   否则附件功能上线即不可用。
2. **INT-11 的恢复演练必须同时恢复 PostgreSQL 和 MinIO。** 这条谁也替不了：只恢复数据库的
   结果是「文字都在、每张图都碎」，而这种半恢复如果没在演练里出现过，就会在真实事故里出现。

### D-1 → S-19 · Admin 可读 L0，并且留痕

**你的答复**：补读审计。

**结论**：保留现在的实现（**Admin 可读本租户任意日志，包括别人的 L0 私密草稿**），
**并补上读审计**；设计 §5.4 那一行已改成指向 §6.3，两句话不再打架。

**读审计的口径**（这是这条决策里唯一需要设计的地方）：只记**换成普通 Member 就读不到**
的那些读——判定方式是把同一条规则再跑一遍、把读者的角色降成 Member，读不到才记。于是：

| 场景 | 记不记 | 为什么 |
|---|---|---|
| Admin 打开别人的 L0 私密草稿 | **记** | 正是这条权限的行使 |
| Admin 打开全租户可见（L3）的日志 | 不记 | 任何同事都能做的读 |
| Admin 打开一篇**被显式授权**给自己的 L1 | 不记 | 他是被点名的，没用到 Admin 权力 |
| Admin 打开自己所在空间的 L2 | 不记 | 同空间任何成员都能做的读 |
| 列表 / 搜索一次带出 14 篇私密日志 | 记**一行**，列出这 14 个 id | 那是一次行为，一行一条会把真正要看的埋掉 |

覆盖面：详情 · 版本列表 · 差异 · 授权名单 · 列表 · 搜索命中 · **附件下载**（文件就是
内容）。审计行是 `log.read_by_admin`，带 `via` 说明从哪个入口读的。

⚠️ **一个必须知道的后果**：**读会写。** 一条读路径在——且仅在——真的记了东西的时候提交
事务。这就是把审计做得这么窄的原因：如果连正常浏览都记，那张表会被刷满，而真正要查的
那几行反而找不到。

### D-2 → S-20 · 定时任务以系统身份跑

**你的答复**：以 root 跑（或 admin）。

**结论**：给调度器一个**自己的身份**（`ActorType.SYSTEM` + `Origin.SYSTEM` + 一份短能力
清单），而不是借某个 Admin 的账号。入口 `scripts/purge_log_versions.py`，cron 一行，
90 天清理现在能跑了。

**为什么是「系统」而不是「某个 admin」**：借来的账号会让审计行记到一个当时在睡觉的人
头上——**那比没有审计更糟，因为它是错误的证据**。系统身份的审计行如实记成 `system`。

**这个身份买到了什么、没买到什么**（说清比含糊好）：能力清单是任务自己声明的，所以它
**不是**对「这个任务能不能跑」的第二道判断——自授权的身份从来都不是。它买到的是三样：
① 如实的归属；② 一道硬墙——`origin` 必须是 `SYSTEM`，所以**任何请求都不可能以系统身份
运行**，哪怕有 bug 把 actor 类型弄对了也不行；③ 一份可评审的短清单（今天只有一项能力）。

Admin 手动跑仍然可以，审计行会如实记成那个人。`--dry-run` 用**同一条选择语句**只计数不
删除，所以演练不会「报 0 而真跑删掉几千行」。

### D-3 → S-21 · 访客看不到整个工单看板

**你的答复**：不能。

**结论**：**Guest 只能读自己是负责人或报告人的工单**；Admin 与 Member 仍是全租户可见。

### D-5 → S-23 · 状态机补两条流转

**你的答复**：采纳建议。两条都加了：`Done → Todo`（重开）与
`In Review → In Progress`（评审打回）。都不需要新状态，所以**冻结的枚举一个字没动**。

- **重开保留原编号与 `rev` 历史**——它是同一张工单，只多写一行状态历史。这正是这条边的
  意义：没有它，人只能新建一个重复工单，而重复工单是 INT-8 的计数看不穿的东西。
- **两条都不要求填理由**（只有 Blocked / Won't Fix 要）。给重开加理由要求看起来像严谨，
  实际会让「新建一个重复单」重新变成更省事的那条路。
- ⚠️ **S1 从此没有终态了**：Done 与 Won't Fix 都能回到 Todo。这句要明说，因为「这单还会
  回来吗」是看板、指标和 webhook 消费方都要问的问题。
- 原先钉住这两条边不存在的两个测试，和设计 §7.2 在同一次改动里一起改了——这就是那套
  机制在正常工作，不是障碍。

  ⚠️ **补一条当时没写的**：bootstrap 拒绝往已存在的租户里加第二个 Admin，而 AC-4 又拒绝
  停用/降级最后一个 Admin。所以**上线后第一件事是从产品里再造一个 Admin**（邀请或提升），
  否则唯一的管理员账号出问题时没有第二个入口。

## 2. 还需要你做的五项

### P-1 R-2 每月账号复核 + 离职 checklist

没有 SSO，**离职/转岗不会自动停用账号**；自助注册让这条更重要，因为账号不是 Admin
一个个发出去的，Admin 未必知道有谁在。

已认领：**WANGLI**。要落地的两件事：① 每月一次账号复核；② 把「在 Relay 停用账号」
加进离职 checklist。

代码这边支持得上，而且现在**从界面上就能做**：`POST /web/admin/users/{id}/deactivation`
会**同时终止该用户所有会话**并返回终止了几个——停用不是只改一个状态位，被停用的人下一个
请求就是 401。另外「租户内最后一个 Admin」不能被停用也不能被降级。

### P-2 AI 角色在 S1 无事可做

计划里原有的风险，不是我发现的：S1 没有 BOT、没有 RAG、没有网关路由，**AI 这个角色整个
S1 没有活**。要么早点给 RAG 的分块/检索预研，要么并进 API/前端。让它空到 BOT 开工，
会让 BOT 的 10 pd 看起来像凭空出现。

**现在有一个具体的去处**：前端 13 pd 全部可以开工了（HTTP 层已通），API-1/2/3 也可以
并行。

### P-3 双轨试用的观察项：通知看不见就开邮件

F-1 只做站内信有一个必须正视的后果：**站内信要求人主动进平台才看得到**。所以 S1 的采纳
形态只能是「团队每天会打开 Relay」，不是「Relay 会来找人」。

**这条后果是可消除的**：发信通道存在（F-5），聚合窗口和投递状态机现在就按多渠道建好了，
**补上邮件通知约 0.5 pd**（NT-3）。

**要你做的**：把「通知触达」写进双轨试用的观察项。如果第 6 周的反馈是「我从来没看见
通知」，最便宜的解法是**打开邮件通知，而不是等 BOT**——否则团队会一边忍受触达不足，
一边等一个还有 4 周才到的机器人。

### P-4 LOG-9 验收前人工抽检 10 篇

S-16 定的计数口径是**勾选 + 正文 ≥ 300 字符**自动计入，代码里是 `KNOWLEDGE_MIN_BODY`，
和 INT-8 看板用同一个常数所以不会打架。现在也能直接读：
`GET /web/logs/knowledge-count`。

口径之外的那一半是人的：**验收前抽检 10 篇**确认质量。这条要在验收会**之前**做，
不是会上临时对齐。

### P-5 要不要砍掉 LOG-7 / TKT-6

计划里的 cut candidate #1（LOG-7 模板，1 pd FE）和 #2（TKT-6 看板拖拽，2.5 pd FE）。
前端还没开工，所以现在砍仍然是最省的时候。

**我的建议**：**先不砍，但把它们排在最后。** HTTP 层实际花了 4 pd（估的是 3–4），
如果第 7 周排期紧，这 3.5 pd 就是最自然的对冲——而到那时你会有真实的前端速度，
比现在猜要准。
