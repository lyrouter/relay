## 0. 一句话规则

**S1 期间 Jira 不停。** 工单在两边都有，日志只在 Relay。
这不是"过渡期的妥协"，是[明确的决策](relay-s1-design.md#121-决策记录全部采纳建议)（S-9）：
Jira 下线要等 WeCom 通知，那是 BOT 的事，不在 S1。

所以：

| 东西 | 放哪 | 为什么 |
|---|---|---|
| **日志 / 排查记录 / 复盘 / 设计文档** | **只在 Relay** | Relay 有版本历史、全文检索、L0–L3 分享；这是 S1 想建立的习惯 |
| **工单** | **两边都有**，Relay 为主 | Relay 是新的，还没被信任；Jira 是回退路径 |
| **需要外部系统读写的工单** | **只在 Relay** | 只有 Relay 有 API（`/api/v1`），Jira 那边没人对接 |

⚠️ **双轨的代价要说清**：同一件事写两遍。这是有意接受的成本，换的是"Relay 出问题时
工作不停"。如果第 6 周大家觉得 Relay 够稳，砍掉 Jira 那一份是 S1 之后的决定，不是现在。

## 1. 每天

### 所有人

1. **早上打开 Relay 看未读**（右上角"未读 N"）。
   ⚠️ **S1 只有站内信**（F-1）：Relay **不会**主动找你。被指派、被 @提及、你关心的
   工单状态变了，都只在这里出现。这一条是 [P-3](relay-s1-owner-actions.md#p-3-双轨试用的观察项通知看不见就开邮件)
   要观察的东西 —— 如果你发现"我从来没看见通知"，**请直接说**，这正是我们要的反馈，
   补邮件通知只要半天（NT-3）。
2. **写日志。** 一天一篇日报，或者一次排查一篇记录。有模板，不用从空白开始。
3. **工单只在 Relay 里流转状态。** 在 Jira 里也改一次，是为了让 Jira 那份不失真。

### 谁负责什么

| 角色 | 每天 | 每周 |
|---|---|---|
| 开发 | 日报 + 排查记录；工单状态自己流转 | —— |
| 负责人（assignee） | 分诊新单：定类型、优先级、负责人 | 看一眼"我的工单"里积压的 |
| Admin | 审批待激活账号（自助注册的会进 pending） | 账号复核（[P-1](relay-s1-owner-actions.md#p-1-r-2-每月账号复核--离职-checklist)） |

## 2. 三条容易踩的规则

### 2.1 "回滚"不是撤销

日志的版本历史里，**回滚会新增一个版本**，不会删掉后面的版本
（[§6.2](relay-s1-design.md#62-版本与回滚log-4)）。历史永远不会被改写 —— 这是有意的：
"某人回滚掉了我半天的工作"这件事在 Relay 里不可能发生，因为那半天的工作还在版本列表里。

### 2.2 可见范围默认最窄

新日志是 **L0（仅自己 + Admin）**。要给同事看，得自己往上调：

| | 谁能看 |
|---|---|
| L0 私密 | 作者本人 + Admin |
| L1 指定 | 作者 + 被点名的人 + Admin |
| L2 空间 | 作者 + 该空间成员 + Admin |
| L3 全租户 | 公司里所有人 |

⚠️ **Admin 能看 L0，并且会留痕**（S-19）。这不是后门：Admin 读别人的私密日志会写一行
`log.read_by_admin` 审计。**你的日志不是完全私密的，但任何人来看都留下记录。**
写之前知道这一点，比事后发现好。

### 2.3 完成不是终点

`Done` 和 `Won't Fix` **都能回到 Todo**（S-23）。所以：

- 看板上的"已完成"列不是归档，是"目前认为做完了"；
- 重开保留原编号（`RL-331` 还是 `RL-331`）和全部历史 —— 不要为了重开新建一张单，
  重复单是指标看不穿的东西；
- **重开不需要填理由**（只有 `Blocked` / `Won't Fix` 要）。这是故意的：给重开加门槛，
  只会让"新建一张重复单"重新变成更省事的那条路。

## 3. 出问题怎么办

| 症状 | 先做什么 | 不用做什么 |
|---|---|---|
| 图片裂了 / 附件打不开 | 刷新页面重新取链接（下载链接只有 5 分钟有效） | 不用重新上传 |
| "该工单已被其他人修改" | 页面已经自动载入最新内容，看一眼对方改了什么，再决定要不要重提 | 不要反复点保存 —— 这个提示正是为了防止盖掉别人的修改 |
| 收不到验证邮件 | 找 Admin 确认 SMTP 是否已配（O-2） | 不要反复注册，会被限流 |
| 通知没看见 | **说出来**，见 §1 | 不用等 BOT |
| 页面报"服务出现意外错误" | 截图 + 时间，报给开发 | 不用重试很多次；500 是我们的 bug |

**报 bug 就在 Relay 里建工单**，`type=bug`。这也是在用产品本身。

## 4. 对外集成（有外部系统要读写工单时）

S1 有一套冻结的公开 API：`/api/v1`。

1. 找 Admin 在**账号设置 → API token** 里建一个**服务 token**（`rly_s_…`），
   明文只显示一次；
2. 权限范围按需勾：`tickets:read` / `tickets:write` / `comments:write` / `meta:read`；
3. 对接文档：`make serve` 之后 `/docs`，契约快照在仓库根的 `openapi.json`。

**三件必须告诉对接方的事**：

- **租户从 token 推导。** 请求里出现 `tenant_id` 一律 **400**，不是被忽略。
- **建单请带 `Idempotency-Key` 和 `external_ref`**，两个都要：前者防网络重试，
  后者防上游重放（用户连点三次）。只带一个就会出现重复单。
- **截图不走 API**（S1 没有附件端点）。截图存在对接方那边，URL 贴进工单描述里。

⚠️ **服务 token 拿得到 `/comments`。** "不给终端用户看内部评论"是对**消费方**的约束，
不是 API 的能力边界 —— 写进你们自己的对接文档，不要指望 API 表面替你拦住。

## 5. 第 6 周要回答的问题

这不是满意度调查，是三个会改变排期的问题（[P-3](relay-s1-owner-actions.md#p-3-双轨试用的观察项通知看不见就开邮件) / [P-5](relay-s1-owner-actions.md#p-5-要不要砍掉-log-7--tkt-6)）：

1. **通知你看得见吗？** 如果多数人答"没注意到"，就打开邮件通知（NT-3，约半天），
   不等 BOT。
2. **日志你写了吗？写的时候卡在哪？** 编辑器、模板、检索，哪个不好用。
3. **Jira 那一份，你还在写吗？** 如果大家已经只在 Relay 里操作，那是 S1 之后
   下线 Jira 的第一个证据。

验收看板（Admin → 仪表盘）会给出数字：**周活跃创作者占比**（分母是"已激活账号"，
机器主体不计入人头）、本周日志数、工单数、知识库候选数。
口径写在代码里而不是在验收会上现场商量 —— 见 `relay/app/metrics.py`。

⚠️ 数字之外还有一半是人的：**验收前人工抽检 10 篇知识库候选**
（[P-4](relay-s1-owner-actions.md#p-4-log-9-验收前人工抽检-10-篇)），计数不等于质量。
